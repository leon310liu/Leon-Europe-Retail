# Leon Europe GTM AI — Engineering Fix P0

日期：2026-08-25
状态：待实施
性质：工程问题，不属于 Prompt / Conversation Skill

## 1. 已确认问题

2026-08-24 测试中出现连续两次回答生成失败。

后台证据显示：

- 服务端返回 502；
- OpenAI 返回 incomplete_details.reason = max_output_tokens；
- 当前单轮最大输出设置为 2800 tokens；
- 模型已经开始正常回答，但结构化 JSON 在达到输出上限后被截断；
- 网页无法解析不完整 JSON，于是向用户显示“这次回答没有成功生成”。

因此，这至少不是“Leon AI 不会回答”，而是应用层输出预算与结构化响应机制导致的稳定性问题。

## 2. P0 原则

不能允许用户完成多轮咨询后，在关键答案处因为后台状态或 JSON 被截断而整轮失败。

技术上应给系统足够的输出空间；产品上仍要求用户可见回答保持短。

即：

> Backend capacity up, frontend verbosity down.

## 3. 待实施修复

### A. 输出预算

- 提高后台安全输出上限；
- 不因此放宽用户可见回答长度；
- 普通对话继续由 Conversation Mode 控制为短回答。

### B. 压缩 Consultation State

- 后台 Consultation State、信息充分度、知识缺口、decision_basis 等字段必须压缩；
- 避免每轮重复生成越来越长的历史状态；
- 优先存储结构化摘要，而不是复制完整分析过程。

### C. max_output_tokens 截断处理

检测 incomplete_details.reason = max_output_tokens 时：

1. 不直接把整轮判为失败；
2. 自动采用更高额度重试一次，或使用压缩结构化状态的降级请求；
3. 如用户可见答案已经完整，应优先保住答案；
4. 后台状态可单独降级，而不能拖垮用户回答。

### D. 错误恢复

失败时：

- 保留用户最后一次输入；
- 提供“重试本轮”；
- 可提供“缩短回答后重试”；
- 不要让输入从界面消失；
- 不要只显示无法诊断的统一错误。

### E. 服务端观测

每个 /api/chat 请求建议记录：

- request_id；
- 会话轮数；
- 输入字符数 / 估算 tokens；
- 输出 token 上限；
- 首字时间；
- 总耗时；
- 输出字符数；
- HTTP 状态码；
- incomplete_details；
- 是否触发知识检索；
- 是否重试；
- 最终成功/失败原因。

## 4. 后续回归测试

修复后至少测试：

- 1 / 5 / 10 / 15 轮上下文；
- 500 / 1000 / 2000 / 4000 字目标输出；
- 有知识库检索 / 无知识库检索；
- 普通短回答；
- 用户明确要求完整 GTM 方案；
- max_output_tokens 人工触发；
- 重试后是否保留用户输入和对话状态。

## 5. 验收标准

P0 修复完成至少满足：

1. 普通咨询不因结构化后台字段过长而失败；
2. max_output_tokens 截断可被识别并自动恢复或降级；
3. 用户问题不会因失败而丢失；
4. 前台短回答与后台输出容量相互独立；
5. 错误日志能够明确区分输出截断、API错误、服务端错误、网络中断和前端解析错误。

本文件只记录工程修复要求，不应被直接写入 Leon AI 的 Master Instructions。
